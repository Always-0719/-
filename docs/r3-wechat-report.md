## 1. 机制核实（与 PRD 假设逐条对照）

| PRD 假设 | 核实结果 |
| --- | --- |
| 一次性订阅消息 | 成立。用户每点一次"允许"= 获得**该模板** 1 条下发额度；额度按模板分格计量，服务端必须精确到 (user, template) 记账，不能笼统记"已订阅" |
| 每次打开小程序引导续订（收集额度） | 成立且是标准做法。`wx.requestSubscribeMessage` 必须在**用户点击回调**中调起（基础库 ≥2.8.2），页面加载自动弹窗会被拒；一次调用最多 3 个 tmplId；勾选"总是保持以上选择"后额度可静默累积 |
| 额度不足降级邮件+站内 | 必要且可行。下发走服务端 `subscribeMessage.send`（需 access_token，7200s 有效须缓存；需用户 openid）；额度耗尽/用户拒收返回错误码（43101 类），用户关闭总开关返回 20004——两者都必须触发降级而不是丢提醒 |
| 长期订阅可否替代 | **不可**。长期订阅仅向政务民生、医疗、交通、金融、教育等**线下公共服务**开放，个人主体无申请资格；学生协作工具不在其列。不要按长期订阅设计方案 |
| 个人主体可用性 | 可用。个人主体小程序可正常使用一次性订阅消息（有 2026-09 个人主体实战案例佐证）；受限的是支付与长期订阅，不影响本场景 |

## 2. 关键阻断点：H5 载体收不到额度

- `requestSubscribeMessage` 是**小程序专属 API**，H5/公众号网页无此能力（uni-app 平台差异表明确 H5 不支持）。
- 本项目已确认"H5 先行"，意味着：**即使后端通道全部就绪，也没有任何入口收集微信额度**。微信渠道的可行性不取决于后端，而取决于小程序壳何时存在。
- 小程序内嵌 web-view 承载 H5 时，订阅授权仍需由小程序原生按钮触发（web-view 内页面无法直接调起），需要一层原生壳页面做"续订引导"。

## 3. 对 F17 排期与父 PRD 的影响

1. MVP 第 2–3 周：F16 站内+邮件为唯一真实通道；`WECHAT_ENABLED=false`；subscribe_quota 表与收集端点照常建（步骤 16），H5 设置页放续订引导占位说明。
2. 第 4–5 周（步骤 16）：若届时小程序壳 + AppID + 模板 ID 就绪 → 真机验证一次下发并打开 flag；否则 F17 以"降级链完整+单测覆盖"交付，微信真实触达顺延，**上报父 PRD 修订**（R3 结论：条件可行，依赖小程序载体）。
3. 提醒永不丢：任何微信发送失败/无额度路径必须回落邮件+站内（步骤 16 单测锁定）。
4. 额度记账粒度修正：PRD 的 subscribe_quota 按 user 记 remaining；接入真实微信时须细化为按模板记账（MVP 单模板场景下两者等价，登记 decisions.md 备忘）。

## 4. 缺口清单（真机验证前置条件）
